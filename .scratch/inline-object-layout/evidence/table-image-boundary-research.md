# Table → inline-image paragraph spacing: source research

## Finding and limits

**Clarification after research:** the user identified `reviewed-table-image-boundary.png` as a screenshot of a **draft DOCX in WPS Writer**, not the polished final output. It is therefore not evidence that the final `figure_image` spacing failed. Read-only inspection confirms that `image-fixed-draft.docx` uses `CaptionedFigure` → `Figure` → `Normal`, with no spacing on those styles; `image-fixed-final.docx` uses `figure_image`, with before 6 pt (`w:before="120"`), after 5 pt and automatic 1.5-line leading. Neither image paragraph has direct spacing. The research below addresses the initial, now-unsubstantiated premise of missing spacing in the final artifact. No additional production change is justified by this screenshot; final rendered separation remains pending manual review. This investigation did not render or mutate a DOCX, run suites, install exporters, or automate/launch Word.

**[INFERENCE] An effective explicit 6 pt before-spacing should contribute above the following paragraph even when its predecessor is a nonfloating table.** The sources below provide a general paragraph-spacing requirement and a concrete renderer path retaining upper spacing after a table. None of the researched primary sources establishes a blanket “after table → discard explicit before-spacing” rule. However, the specification’s paragraph-to-paragraph maximum rule is not an explicit table-border-to-image-pixel algorithm. It therefore does **not** certify an exact visible 6 pt border-to-background gap, nor establish the screenshot’s cause.

## Primary-source requirements

1. **Explicit spacing and inheritance.** Microsoft’s ISO/IEC 29500 excerpt for [`spacing`, §17.3.1.33](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines?view=openxml-3.0.1#remarks) says spacing “**shall be applied to the contents of this paragraph when it is displayed by a consumer**”; when omitted directly, “**each of its values is determined by the setting previously set at any level of the style hierarchy**.” Thus absence of direct `w:spacing` does not itself negate style-based before-spacing. The same excerpt’s “**When determining the spacing between any two paragraphs … use the maximum**” rule concerns two paragraphs, not a table frame and the next paragraph. It is not evidence that a table cancels before-spacing or that the last cell’s paragraph is the previous body paragraph.

2. **Automatic before-spacing can defeat explicit values.** [`BeforeAutoSpacing`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines.beforeautospacing?view=openxml-3.0.1#remarks): “**any value in before or beforeLines is ignored, and the spacing is automatically determined by the consumer**.” Resolve the enabled automatic setting through direct properties, style/`basedOn`, and defaults; do not infer it merely from `lineRule="auto"`, which controls a different property. The documented default, if automatic before-spacing is never specified in the hierarchy, is off.

3. **Word has a relevant inheritance exception.** Microsoft’s [MS-OI29500 §2.1.60](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/264a0139-8174-4574-b20d-ab778e770931) states: “**During Style Hierarchy application, Word overrides non-line unit spacing with related non-zero line unit spacing that is applied earlier in the Style Hierarchy order.**” Therefore inspect inherited `beforeLines`, not only direct `before`. [`BeforeLines`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines.beforelines?view=openxml-3.0.1#remarks) defines its units as “**hundredths of a line**.” This is a conditional precedence hypothesis, not an observed property of this document.

4. **Contextual spacing is a same-style paragraph condition.** [`contextualSpacing`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.contextualspacing?view=openxml-3.0.1#remarks) says before/after space “**should not be applied when the preceding and following paragraphs are of the same paragraph style, affecting the top and bottom spacing respectively**.” Unspecified through the entire hierarchy means spacing is not ignored. This does not document table-wide suppression; the matching-neighbor condition must actually exist.

5. **The named compatibility toggles are narrower than an after-table rule.**
   - [`doNotUseHTMLParagraphAutoSpacing`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.donotusehtmlparagraphautospacing?view=openxml-3.0.1#remarks) concerns automatic spacing “**defined by a value of true … on the beforeAutospacing and/or afterAutospacing attributes**.” Enabled, it maps automatic before to 5 pt and after to 10 pt. It does not independently override an explicit 6 pt when paragraph auto-spacing is off. Do not toggle it globally as a speculative fix.
   - [`suppressTopSpacing`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.suppresstopspacing?view=openxml-3.0.1#remarks) ignores minimum/exact **line height** “**for the first line on each page**”; [`suppressSpacingAtTopOfPage`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.suppressspacingattopofpage?view=openxml-3.0.1#remarks) similarly concerns `atLeast`. Neither states a generic table-boundary exception to paragraph before-spacing.
   - [`suppressSpBfAfterPgBrk`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.suppressspacingbeforeafterpagebreak?view=openxml-3.0.1#remarks) applies to a run-level page break in a paragraph whose content follows that break: “**if the line with the page break has no content, then … before … is simply ignored**.” A table immediately above an image on the same displayed page is not by itself that condition.

6. **Inline metrics and outside spacing are distinct.** [`wp:inline`, §20.4.2.8](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.wordprocessing.inline?view=openxml-3.0.1#remarks): an inline drawing “**affects the line height and layout of its line (like a character glyph of similar size)**.” Microsoft’s [paragraph dialog documentation](https://support.microsoft.com/en-us/word/adjust-indents-and-spacing) describes `At least` as the minimum needed “**to fit the largest font or graphic on the line**” and `Exactly` as fixed line spacing. Consequently allowing image-sized line height fixes clipping/allocation, but does not prove the external table-to-image gap is present. Increasing 1.5 arbitrarily would mix these separate mechanisms.

## First-party renderer cross-check (not viewer identification)

The inspected LibreOffice source is useful counter-evidence to a universal suppression claim:

- [`SwFlowFrame::CalcUpperSpace`, flowfrm.cxx](https://github.com/LibreOffice/core/blob/master/sw/source/core/layout/flowfrm.cxx#L1616-L1699) retains the following paragraph’s resolved `pAttrs->GetULSpace().GetUpper()` in both the additive and maximum-spacing branches. [Its same-style helper](https://github.com/LibreOffice/core/blob/master/sw/source/core/layout/flowfrm.cxx#L1482-L1524) obtains the predecessor’s paragraph style only for a text frame. **[INFERENCE, scoped to this path]** a preceding table frame does not itself zero positive upper spacing or create a matching paragraph style.
- [The page-top collapsing helper](https://github.com/LibreOffice/core/blob/master/sw/source/core/layout/flowfrm.cxx#L1537-L1561) comments “**Anything related to tables is skipped simply to avoid potential disaster**.” It is not an after-table-suppression explanation.
- [Writer’s import handling](https://github.com/LibreOffice/core/blob/master/sw/source/writerfilter/dmapper/DomainMapper_Impl.cxx#L2593-L2629) says “**apply AutoSpacing: it has priority over all other margin settings**” and “**apply INHERITED autospacing only if top margin is not set**.” Its zero-auto-before case includes the first paragraph **inside a table cell**, not a body paragraph following a table. This distinguishes importer precedence from layout suppression.

These are mutable upstream source links, inspected during this research, not a pinned installed-renderer audit or a rendering result.

## Ranked hypotheses and falsifiers

1. **Target viewer does not apply the resolved style margin at this boundary, or maps its line/image box differently.** Prediction: identical content polished with before 0 vs 6 does not move the image top in that viewer, despite the intended XML delta. A visible repeatable increase falsifies complete before-spacing suppression. This is currently an unproven renderer/layout hypothesis, not identification of the application.
2. **The effective before-spacing is not actually explicit 6 pt** because of direct before/auto/line-unit properties or inherited contextual spacing. Prediction: the property trace identifies an applicable overriding condition; removing only that condition on a diagnostic copy restores response to 6 pt. A complete effective-property trace with those conditions absent/disabled strongly falsifies this explanation. Style-only `120` is not sufficient evidence either way.
3. **The displayed artifact differs from the traced output, or an import/view conversion loses the property.** Prediction: the exact newly named 0/6 pair responds differently from the reviewed artifact, or the loaded/imported representation omits the property. Matching file provenance plus the same result for both fresh copies lowers this hypothesis. Do not dismiss the reported screenshot as stale without this evidence.
4. **A page-break/top-of-page compatibility exception applies.** Requires its documented geometry/run-break condition and relevant setting. The screenshot’s same-page table above the image makes the named page-top mechanisms a poor fit; absent conditions falsify them. Do not change these toggles merely because their names mention spacing.

## Minimal discriminating probes and recommendation

**Do not change production yet. Start with one existing-pipeline, one-variable pair**, both polished from the same `image-fixed-draft.docx`, same emitted Markdown, same snippet configuration, different output names. Existing deep merge is documented in `references/ToolSpec.md`, “Paragraph allocation and style overrides.” Override only:

```yaml
styles:
  style:
    figure_image:
      space_before_pt: 0  # A; B is exactly 6
```

Keep after=5, automatic leading=1.5, dimensions, image bytes/ALT, `wp:inline`, captions, equations, tables, and sections identical. The expected role-style difference is before `0` versus `120`; preserve unrelated existing direct properties and inspect the effective winner before interpreting the pair. Use the existing `snippet-docx polish ... --snippet ... --md image-fixed-anchored.md --out <distinct-name>.docx` route. **These probes are recommendations, not artifacts generated or checks run by this research.**

The user manually opens the exact pair in the same target application/view/zoom and compares table-bottom-border → image-background-top. No agent-driven Word review. Outcomes:

- **B gains clearance:** the viewer can apply before-spacing; investigate the original artifact’s effective properties/provenance before increasing values.
- **A and B are indistinguishable:** next compare **the same 6 pt inherited from the style versus direct `before="120"` on only the image paragraph**, using disposable input copies through the existing polish path, which intentionally preserves direct before/after. This does not change the requested amount. If only direct works, isolate a style-resolution/import problem; no sourced rule justifies blanket direct formatting of every body paragraph.
- **Both 6 pt placements fail:** compare the same drawing paragraph after the table versus after one ordinary, nonempty text paragraph in a disposable minimal fixture, with 6 pt and all object properties unchanged. Response after text only isolates the boundary; failure in both points to general style/spacing mapping or image-line metrics. Do not insert a blank spacer or substitute a floating drawing.

**Specific minimal fix, conditional on evidence:** remove/reset only a demonstrated defeating auto/line-unit/contextual property at the affected image-role resolution seam, or correct the demonstrated renderer/style-resolution seam while retaining 6 pt. If no such condition is present, the next deliverable is the A/B target-viewer result—not a larger multiplier, blanket table/body spacing patch, resized drawing, or invented padding.

No new exporter is warranted for the first decision. XML proves serialized properties, not painted separation; HTML or another renderer can be a differential diagnostic only, never exact target-viewer proof. No unknown exporter was installed or invoked, and Word-backed export/refresh remains prohibited.
